# Inventory Collector — Schema V2 Design

Status: **DRAFT** — not yet applied, for discussion.

## What this document is

A proposal for evolving the SQL schema and pipeline to support:

1. **History.** Today's tables are upserted in place; previous values are lost. V2 keeps every collected snapshot until a retention policy expires it.
2. **Stable joins.** Every metric currently joins to "the rest of the inventory" via `ComputerName` text. V2 introduces a `Computers` master table, named indexes, and FK constraints.
3. **Auditability.** Every row in every fact table will be traceable back to a specific collection run (which endpoint, when started, what failed).
4. **Frontend readiness.** A small set of views (`vCurrent*`) expose the current-state surface a UI cares about, decoupling the app from the underlying snapshot mechanics.

What this is **not**:

- A frontend design doc — that comes later, on top of the views defined here.
- A type-mapping spec — types are listed as guidance, the full mapping table comes during implementation.
- A perf doc — bulk-load (`MERGE` / `SqlBulkCopy`) is mentioned but out of scope for v2.

## Design choices (decisions to confirm)

| # | Choice | Default | Trade-off |
|---|---|---|---|
| 1 | Join column | `ComputerName` as text (UNIQUE) | INT `ComputerId` FK is faster at scale but adds a lookup per row at write time. Defer. |
| 2 | History model | Append-only fact tables + current-state views | Simpler than SCD Type-2; storage grows linearly with snapshots. |
| 3 | Snapshot grain | One per `GetInventory` run per computer | Natural unit. Matches the existing pipeline shape. |
| 4 | Run identity | `RunId` (`UNIQUEIDENTIFIER`) generated by the collector | Easy to generate everywhere, no central allocator needed. |
| 5 | Retention | Keep latest N runs per computer (configurable) | Cheaper than time-based. Adjust per environment. |
| 6 | Type fidelity | Use real SQL types where the JSON property has a stable type (`DATETIME2`, `DECIMAL`, `BIGINT`) | Less storage, real SQL operations, but the schema-derivation code grows. |

If any of these defaults are wrong for your environment, change them here before we touch DDL.

## V2 schema sketch

Two new infrastructure tables plus an evolved version of every existing fact table.

### `Computers` — master

```sql
CREATE TABLE dbo.Computers (
    ComputerName   NVARCHAR(64)  NOT NULL PRIMARY KEY,
    FirstSeenAt    DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME(),
    LastSeenAt     DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME(),
    LastRunId      UNIQUEIDENTIFIER NULL,
    IsActive       BIT           NOT NULL DEFAULT 1,
    DeactivatedAt  DATETIME2(3)  NULL
);

CREATE INDEX IX_Computers_LastSeenAt ON dbo.Computers (LastSeenAt);
CREATE INDEX IX_Computers_IsActive   ON dbo.Computers (IsActive) WHERE IsActive = 1;
```

- `ComputerName` is the natural key. Stays as the join column in every fact table.
- `LastSeenAt` lets a frontend / monitoring answer "which servers haven't reported in 7 days" with a single query — no per-table aggregation needed.
- `IsActive` is set to `0` by a scheduled job when `LastSeenAt` is older than a configurable threshold. Reactivates automatically if data comes back. Lets the frontend hide decommissioned hosts without deleting history.

### `CollectionRuns` — every collection cycle

```sql
CREATE TABLE dbo.CollectionRuns (
    RunId             UNIQUEIDENTIFIER NOT NULL PRIMARY KEY,
    ComputerName      NVARCHAR(64)     NOT NULL REFERENCES dbo.Computers(ComputerName),
    StartedAt         DATETIME2(3)     NOT NULL,
    CompletedAt       DATETIME2(3)     NULL,
    Status            NVARCHAR(20)     NOT NULL,   -- 'Collecting' | 'Parsed' | 'Loaded' | 'Failed'
    MetricsSucceeded  INT              NULL,
    MetricsFailed     INT              NULL,
    FailedMetrics     NVARCHAR(MAX)    NULL,       -- comma-separated metric names
    LoadedAt          DATETIME2(3)     NULL
);

CREATE INDEX IX_CollectionRuns_Computer_Started
    ON dbo.CollectionRuns (ComputerName, StartedAt DESC);
CREATE INDEX IX_CollectionRuns_Status
    ON dbo.CollectionRuns (Status, StartedAt DESC);
```

- One row per `GetInventory.ps1` invocation on one endpoint. `RunId` is generated on the endpoint (`[guid]::NewGuid()`) and travels with the zip.
- `Status` advances: `Collecting` (set on the endpoint when the run starts) → `Parsed` (set when `ParseInventory.ps1` lands the JSONs) → `Loaded` (set when SQL load finishes) → `Failed` (terminal).
- Failure metadata in `MetricsFailed` / `FailedMetrics` mirrors the existing summary log so it's queryable.

### Fact tables — append-only with `RunId`

Every existing fact table (`InstalledSoftware`, `SystemInfo`, `GroupMembers`, …) keeps its columns and gains three:

```sql
ALTER TABLE dbo.InstalledSoftware ADD
    RunId         UNIQUEIDENTIFIER NOT NULL DEFAULT '00000000-0000-0000-0000-000000000000',
    CreatedAt     DATETIME2(3)     NOT NULL DEFAULT SYSUTCDATETIME();
-- (UpdateTimeStamp is dropped — replaced semantically by CreatedAt + the view layer)

-- FK constraints come after backfill
ALTER TABLE dbo.InstalledSoftware ADD CONSTRAINT FK_InstalledSoftware_Run
    FOREIGN KEY (RunId) REFERENCES dbo.CollectionRuns(RunId) ON DELETE CASCADE;
ALTER TABLE dbo.InstalledSoftware ADD CONSTRAINT FK_InstalledSoftware_Computer
    FOREIGN KEY (ComputerName) REFERENCES dbo.Computers(ComputerName);
```

- `RunId` ties every fact row to its origin run. `ON DELETE CASCADE` means dropping an aged-out `CollectionRuns` row deletes its fact rows — that's how retention works without a separate cleanup script.
- `CreatedAt` is "row was inserted into SQL", not "data was collected". For the data-collected time, join on `CollectionRuns.StartedAt`.
- No more `UpdateTimeStamp`. The old name was misleading (set only on INSERT, never UPDATE); semantics are split between `CreatedAt` and the natural-key view layer.

### Natural-key uniqueness

The previous `KeyColumnsMap` was a script-side convention. In V2 it becomes a constraint per table:

```sql
-- Example: one row per (RunId, ComputerName, DisplayName, DisplayVersion)
CREATE UNIQUE INDEX UX_InstalledSoftware_Natural
    ON dbo.InstalledSoftware (RunId, ComputerName, DisplayName, DisplayVersion);
```

Per-table natural keys (derived from today's `KeyColumnsMap`, **always prefixed with `RunId`** so re-running a job is idempotent within one run but doesn't collide with prior runs):

| Table | Natural key |
|---|---|
| `Computers` | `ComputerName` |
| `CollectionRuns` | `RunId` |
| `SystemInfo` | `RunId, ComputerName` |
| `DiskSpace` | `RunId, ComputerName, Drive` |
| `InstalledSoftware` | `RunId, ComputerName, DisplayName, DisplayVersion` |
| `InstalledUpdates` | `RunId, ComputerName, Title` |
| `Services` | `RunId, ComputerName, Name` |
| `AutoRunInfo` | `RunId, ComputerName, Name` |
| `LocalUsers` | `RunId, ComputerName, UserName` |
| `GroupMembers` | `RunId, ComputerName, GroupName` |
| `ScheduledTasks` | `RunId, ComputerName, TaskPath, TaskName` |
| `PersonalCertificates` | `RunId, ComputerName, Thumbprint` |
| `ShareAccessInfo` | `RunId, ComputerName, ShareName` |
| `UserProfileList` | `RunId, ComputerName, Name` |
| `MPComputerStatus` | `RunId, ComputerName` |

### Type fidelity (selected columns)

Today everything that isn't `String/Int32/Bool` is `NVARCHAR(MAX)`. V2 uses real types where the source is stable:

| Column | V1 | V2 |
|---|---|---|
| `Computers.ComputerName` | `NVARCHAR(MAX)` | `NVARCHAR(64)` |
| `SystemInfo.lastbootuptime` | `NVARCHAR(MAX)` | `DATETIME2(3)` |
| `DiskSpace.TotalSize_GB` | `NVARCHAR(MAX)` | `DECIMAL(10,2)` |
| `DiskSpace.FreeSpace_GB` | `NVARCHAR(MAX)` | `DECIMAL(10,2)` |
| `UserProfileList.UserProfileSizeMB` | `NVARCHAR(MAX)` | `DECIMAL(12,2)` |
| `PersonalCertificates.NotBefore` / `NotAfter` | `NVARCHAR(MAX)` | `DATETIME2(0)` |
| `LocalUsers.PasswordLastSet` / `LastLogonDate` | `NVARCHAR(MAX)` | `DATETIME2(0)` |
| `MPComputerStatus.*SignatureAge` | `NVARCHAR(MAX)` | `INT` |
| `MPComputerStatus.*SignatureLastUpdated` | `NVARCHAR(MAX)` | `DATETIME2(0)` |

The schema-generation code (`CreateSQLTableFromJSON.ps1`) gets a richer type switch covering `DateTime`, `Decimal`, `Int64`. Nested arrays / complex objects still serialize to `NVARCHAR(MAX)` JSON — addressed by #15 in the v2 backlog (child tables).

### Current-state views

The view layer is what the frontend reads. Each metric gets a `vCurrent*` view that selects the latest run's rows per computer.

```sql
CREATE OR ALTER VIEW dbo.vCurrentInstalledSoftware AS
WITH LatestRuns AS (
    SELECT r.ComputerName, r.RunId
    FROM dbo.CollectionRuns r
    INNER JOIN (
        SELECT ComputerName, MAX(StartedAt) AS LatestAt
        FROM dbo.CollectionRuns
        WHERE Status = 'Loaded'
        GROUP BY ComputerName
    ) m ON r.ComputerName = m.ComputerName AND r.StartedAt = m.LatestAt
)
SELECT s.*
FROM dbo.InstalledSoftware s
INNER JOIN LatestRuns lr ON s.RunId = lr.RunId;
```

A handful of cross-table views answer the common frontend questions:

```sql
-- Servers that haven't reported in N days
CREATE OR ALTER VIEW dbo.vStaleComputers AS
SELECT c.*, DATEDIFF(HOUR, c.LastSeenAt, SYSUTCDATETIME()) AS HoursSinceLastSeen
FROM dbo.Computers c
WHERE c.IsActive = 1
  AND c.LastSeenAt < DATEADD(HOUR, -25, SYSUTCDATETIME());  -- > 25h gives a 1h grace

-- Fleet software inventory: one row per (software, version) with server count
CREATE OR ALTER VIEW dbo.vFleetSoftware AS
SELECT DisplayName, DisplayVersion, Publisher, COUNT(DISTINCT ComputerName) AS InstalledOn
FROM dbo.vCurrentInstalledSoftware
GROUP BY DisplayName, DisplayVersion, Publisher;

-- Certificates expiring in the next 30 days
CREATE OR ALTER VIEW dbo.vExpiringCertificates AS
SELECT ComputerName, Subject, NotAfter, DATEDIFF(DAY, SYSUTCDATETIME(), NotAfter) AS DaysToExpiry
FROM dbo.vCurrentPersonalCertificates
WHERE NotAfter < DATEADD(DAY, 30, SYSUTCDATETIME());
```

## Pipeline changes

### `GetInventory.ps1`

- Generate `$RunId = [guid]::NewGuid()` at script start.
- Stamp every metric JSON with the `RunId` (top-level property on the record).
- Add a `_collection-meta.json` file in the outer zip containing `{ RunId, ComputerName, StartedAt, MetricsSucceeded, MetricsFailed, FailedMetrics }` — this is what populates `CollectionRuns`.

### `ParseInventory.ps1`

- Read `_collection-meta.json` from each outer zip and emit a `CollectionRuns.json` aggregated file alongside the existing metric JSONs.
- No other change — the `RunId` is already on every row.

### SQL load (`CreateSQLTableFromJSON.ps1` + `UpdateSQLTableFromJSON_new.ps1`)

This is where the biggest change lands. The current upsert model is replaced by:

1. **Upsert `Computers`** from the distinct `ComputerName` values seen across all JSONs in this load. Update `LastSeenAt` and `LastRunId` for known servers.
2. **Insert `CollectionRuns`** from `CollectionRuns.json`. Status `Loaded` set after step 3 finishes.
3. **Insert fact rows append-only.** No more `SELECT COUNT` → `UPDATE or INSERT`. Just `INSERT` with the natural key UNIQUE index providing safety: a re-run inside the same `RunId` becomes a no-op via `INSERT ... WHERE NOT EXISTS` or a `MERGE`. (Re-runs across different `RunId`s create a new snapshot — that's the point.)

Because the fact tables are append-only, the script becomes simpler, not more complex. The KeyColumnsMap goes away (now expressed as DB constraints).

### Retention

A scheduled job (new script `Run-RetentionPolicy.ps1`, called from `scheduler.ps1`):

```sql
WITH RankedRuns AS (
    SELECT RunId,
           ROW_NUMBER() OVER (PARTITION BY ComputerName ORDER BY StartedAt DESC) AS rn
    FROM dbo.CollectionRuns
)
DELETE FROM dbo.CollectionRuns
WHERE RunId IN (SELECT RunId FROM RankedRuns WHERE rn > @RetainRuns);
```

`ON DELETE CASCADE` on the fact-table FKs handles the rest. Default `@RetainRuns = 12` (about 3 months at weekly collection).

## Migration plan

In-place ALTER, three phases. No big-bang drop.

### Phase 1 — infrastructure (zero behavior change)

1. Create `Computers` and `CollectionRuns`.
2. Backfill `Computers` from `DISTINCT ComputerName` across existing fact tables. Set `FirstSeenAt = MIN(UpdateTimeStamp)`, `LastSeenAt = MAX(UpdateTimeStamp)`.
3. `ALTER TABLE` each fact table to add `RunId` (nullable for now) and `CreatedAt` (defaulted to existing `UpdateTimeStamp`, or `SYSUTCDATETIME()` if NULL).
4. Backfill `RunId` with a single "v1-migration" GUID per (ComputerName, MAX(UpdateTimeStamp)) bucket — so each pre-v2 server gets one synthetic "this is what we had before migration" run. Insert a matching row into `CollectionRuns`.
5. Tighten `RunId` to `NOT NULL`. Add FKs.

After Phase 1 the DB has the new shape, existing scripts still work, frontend doesn't exist yet.

### Phase 2 — pipeline emits `RunId`

1. Update `GetInventory.ps1` to generate `RunId` and emit `_collection-meta.json`.
2. Update `ParseInventory.ps1` to aggregate `CollectionRuns.json`.
3. Update load scripts to insert `Computers` / `CollectionRuns` rows.
4. Keep upsert behavior on fact tables for one or two collection cycles to validate.

### Phase 3 — switch fact tables to append-only

1. Drop the `KeyColumnsMap`-based UPDATE branch in the load script.
2. Add the per-table `UNIQUE INDEX (RunId, …)` constraints.
3. Add the `vCurrent*` views.
4. Enable the retention job.

After Phase 3, every collection cycle is a new snapshot. The frontend can be built against the views.

## Open questions

These need answers before Phase 1 starts. Tagging owners as `@you` for the points that are environment-specific.

1. **Retention default**: 12 runs (≈ 3 months at weekly cadence) or longer? Storage cost is real once you have >1k endpoints. — `@you`
2. **`ComputerName` width**: `NVARCHAR(64)` covers NetBIOS (15) + plenty of buffer. If you have FQDN-shaped values in there (`server01.contoso.local`), go to `NVARCHAR(128)`. — `@you`, look at your existing data
3. **`Status` enum** values for `CollectionRuns.Status`: I proposed `Collecting / Parsed / Loaded / Failed`. Anything else worth tracking (`Quarantined` for tampered zips? `Stale` for runs we abandoned?). — open
4. **History granularity for slow-changing data**: `SystemInfo` rarely changes (CPU/RAM are stable). Do we want every snapshot, or "snapshot when value changed"? Add a `vCurrentSystemInfo_Changes` view to expose deltas. — could ship after.
5. **Backfill of `RunId` for pre-v2 data**: synthetic single run per server is the easy answer. Worth doing anything fancier (e.g. one run per `UpdateTimeStamp` cluster)? Probably no. — close.
6. **Should `Computers` use `NVARCHAR PK` or `INT IDENTITY PK + UNIQUE ComputerName`?** I went with the simpler natural key. INT FK is the standard advice; deferred to keep this design boring. — defer unless joins get measurably slow.
7. **Frontend tech**: not for this doc, but the views are designed to be consumed by any client (PowerBI / a small REST API / Blazor / SPA). Worth deciding before view names harden into a public contract. — `@you`, when ready.

## What this doesn't change

- Endpoint code structure (`GetInventory.ps1`'s `Get-*` functions stay as-is, just gain `RunId` on output).
- Zip transport, file share layout, scheduler chain.
- The on-prem vs Azure split — both still need this refactor; Azure variant remains TODO under MSI rewrite.
- Existing tests pass against today's schema. New tests will be added as Phase 1/2/3 land.
