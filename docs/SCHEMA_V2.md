# Inventory Collector — Schema V2 Design

Status: **Decided, ready for Phase 1 implementation.**

## What this document is

A proposal for evolving the SQL schema and pipeline to support:

1. **History.** Today's tables are upserted in place; previous values are lost. V2 keeps every collected snapshot until a retention policy expires it.
2. **Stable joins.** Every metric currently joins to "the rest of the inventory" via `ComputerName` text. V2 introduces a `Computers` master table, named indexes, and FK constraints.
3. **Auditability.** Every row in every fact table will be traceable back to a specific collection run (which endpoint, when started, what failed).
4. **Frontend readiness.** A set of views (`vCurrent*`) expose the current-state surface a UI cares about, decoupling Power BI / Grafana / future apps from the underlying snapshot mechanics.

## Decisions taken

| # | Decision | Value |
|---|---|---|
| 1 | Join column | `ComputerName` text (UNIQUE) |
| 2 | `ComputerName` width | `NVARCHAR(128)` (fleet has mixed NetBIOS + FQDN) |
| 3 | `Computers` PK | `ComputerName` natural key (no INT surrogate) |
| 4 | History model | Append-only fact tables + `vCurrent*` views |
| 5 | Snapshot grain | One per `GetInventory` run per computer |
| 6 | Run identity | `RunId` (`UNIQUEIDENTIFIER`) generated by the collector |
| 7 | Snapshot cadence | Daily (existing scheduled task) |
| 8 | Retention default | 90 runs per computer (~3 months at daily cadence) |
| 9 | Slow-change tables | Snapshot every run anyway — consistent with the rest |
| 10 | High-volume exception | `InstalledUpdates` uses a **differential model** (one row per `(Computer, Title)`, with `FirstSeenRunId` / `LastSeenRunId`) |
| 11 | Indexes | Minimal: PK + natural-key UNIQUE only. Add NCIs reactively as real queries land. |
| 12 | Frontend | Power BI / Grafana / Excel directly against views. No API layer planned. |
| 13 | Type fidelity | Use real SQL types (`DATETIME2`, `DECIMAL`, `BIGINT`) where the JSON property has a stable shape |

## V2 schema

### Two new infrastructure tables

#### `Computers` — master

```sql
CREATE TABLE dbo.Computers (
    ComputerName   NVARCHAR(128) NOT NULL PRIMARY KEY,
    FirstSeenAt    DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME(),
    LastSeenAt     DATETIME2(3)  NOT NULL DEFAULT SYSUTCDATETIME(),
    LastRunId      UNIQUEIDENTIFIER NULL,
    IsActive       BIT           NOT NULL DEFAULT 1,
    DeactivatedAt  DATETIME2(3)  NULL
);
```

- `ComputerName` is the natural key. Stays as the join column in every fact table.
- `LastSeenAt` lets a frontend / monitoring answer "which servers haven't reported in 7 days" with a single query.
- `IsActive` is set to `0` by the retention job when `LastSeenAt` is older than a configurable threshold. Reactivates automatically if data comes back. Lets the frontend hide decommissioned hosts without losing history.

No additional indexes — the PK is sufficient at fleet sizes up to ~100k servers. Add a filtered `WHERE IsActive = 1` NCI if "active server" queries get slow.

#### `CollectionRuns` — every collection cycle

```sql
CREATE TABLE dbo.CollectionRuns (
    RunId             UNIQUEIDENTIFIER NOT NULL PRIMARY KEY,
    ComputerName      NVARCHAR(128)    NOT NULL REFERENCES dbo.Computers(ComputerName),
    StartedAt         DATETIME2(3)     NOT NULL,
    CompletedAt       DATETIME2(3)     NULL,
    Status            NVARCHAR(20)     NOT NULL,   -- 'Collecting' | 'Parsed' | 'Loaded' | 'Failed'
    MetricsSucceeded  INT              NULL,
    MetricsFailed     INT              NULL,
    FailedMetrics     NVARCHAR(MAX)    NULL,       -- comma-separated metric names
    LoadedAt          DATETIME2(3)     NULL
);

CREATE INDEX IX_CollectionRuns_Computer_Started
    ON dbo.CollectionRuns (ComputerName, StartedAt DESC);
```

- One row per `GetInventory.ps1` invocation on one endpoint. `RunId` is generated on the endpoint (`[guid]::NewGuid()`) and travels with the zip.
- `Status` advances: `Collecting` → `Parsed` → `Loaded` (or `Failed` terminal). Set by GetInventory, ParseInventory, and the load script respectively.

### Snapshot fact tables (the standard pattern)

Every existing fact table except `InstalledUpdates` follows the same pattern. They keep their columns and gain three:

```sql
ALTER TABLE dbo.InstalledSoftware ADD
    RunId      UNIQUEIDENTIFIER NOT NULL,
    CreatedAt  DATETIME2(3)     NOT NULL DEFAULT SYSUTCDATETIME();
-- (UpdateTimeStamp is dropped — replaced semantically by CreatedAt + the view layer)

ALTER TABLE dbo.InstalledSoftware ADD CONSTRAINT FK_InstalledSoftware_Run
    FOREIGN KEY (RunId) REFERENCES dbo.CollectionRuns(RunId) ON DELETE CASCADE;
ALTER TABLE dbo.InstalledSoftware ADD CONSTRAINT FK_InstalledSoftware_Computer
    FOREIGN KEY (ComputerName) REFERENCES dbo.Computers(ComputerName);

CREATE UNIQUE INDEX UX_InstalledSoftware_Natural
    ON dbo.InstalledSoftware (RunId, ComputerName, DisplayName, DisplayVersion);
```

- `RunId` ties every fact row to its origin run. `ON DELETE CASCADE` means dropping an aged-out `CollectionRuns` row deletes its fact rows — that's how retention works without a separate cleanup script per table.
- `CreatedAt` is "row was inserted into SQL", not "data was collected". For the data-collected time, join on `CollectionRuns.StartedAt`.
- The old `UpdateTimeStamp` column is dropped. Its name was misleading (set only on INSERT, never UPDATE).

Natural-key UNIQUE indexes, always prefixed with `RunId` so a re-run within the same run is idempotent but doesn't collide with prior runs:

| Table | Natural key |
|---|---|
| `Computers` | `ComputerName` |
| `CollectionRuns` | `RunId` |
| `SystemInfo` | `RunId, ComputerName` |
| `DiskSpace` | `RunId, ComputerName, Drive` |
| `InstalledSoftware` | `RunId, ComputerName, DisplayName, DisplayVersion` |
| `Services` | `RunId, ComputerName, Name` |
| `AutoRunInfo` | `RunId, ComputerName, Name` |
| `LocalUsers` | `RunId, ComputerName, UserName` |
| `GroupMembers` | `RunId, ComputerName, GroupName` |
| `ScheduledTasks` | `RunId, ComputerName, TaskPath, TaskName` |
| `PersonalCertificates` | `RunId, ComputerName, Thumbprint` |
| `ShareAccessInfo` | `RunId, ComputerName, ShareName` |
| `UserProfileList` | `RunId, ComputerName, Name` |
| `MPComputerStatus` | `RunId, ComputerName` |

### `InstalledUpdates` — the differential exception

At daily cadence × 3 months × 1k servers × ~500 updates/server, a snapshot model would produce ~45 million rows for this one table. But updates are *inherently additive* — you don't uninstall a KB normally — so a (Computer, Title) row only ever needs to exist once.

```sql
CREATE TABLE dbo.InstalledUpdates (
    Id               INT IDENTITY(1,1) PRIMARY KEY,
    ComputerName     NVARCHAR(128)    NOT NULL REFERENCES dbo.Computers(ComputerName),
    Title            NVARCHAR(512)    NOT NULL,
    InstalledOn      DATE             NULL,      -- 'Date' in JSON, real DATE type
    ServiceID        NVARCHAR(64)     NULL,
    FirstSeenRunId   UNIQUEIDENTIFIER NOT NULL REFERENCES dbo.CollectionRuns(RunId),
    LastSeenRunId    UNIQUEIDENTIFIER NOT NULL REFERENCES dbo.CollectionRuns(RunId),
    FirstSeenAt      DATETIME2(3)     NOT NULL DEFAULT SYSUTCDATETIME(),
    LastSeenAt       DATETIME2(3)     NOT NULL DEFAULT SYSUTCDATETIME(),
    UninstalledAt    DATETIME2(3)     NULL
);

CREATE UNIQUE INDEX UX_InstalledUpdates_Natural
    ON dbo.InstalledUpdates (ComputerName, Title);
```

Load logic for this table differs from the snapshot tables:

1. **For each incoming row**: `MERGE` on `(ComputerName, Title)`.
   - If exists: `UPDATE LastSeenRunId = @RunId, LastSeenAt = SYSUTCDATETIME(), UninstalledAt = NULL` (clears any prior uninstall).
   - If not: `INSERT` with `FirstSeenRunId = LastSeenRunId = @RunId`.
2. **After all rows for `@ComputerName` in this `@RunId`**:

   ```sql
   UPDATE dbo.InstalledUpdates
   SET    UninstalledAt = SYSUTCDATETIME()
   WHERE  ComputerName    = @ComputerName
     AND  LastSeenRunId  != @RunId
     AND  UninstalledAt   IS NULL;
   ```

   That marks anything we *didn't* see this run as gone.

Result:

- One row per `(Computer, Title)` for the lifetime of that install. Storage stays roughly constant per server.
- `UninstalledAt` lets the frontend say "show me updates that have been removed".
- Re-appearance after an uninstall clears the flag automatically.
- **No `RunId` cascade applies to this table** — it intentionally outlives individual run-deletes. Retention is by `UninstalledAt` age (separate job, default: purge rows where `UninstalledAt < DATEADD(DAY, -180, SYSUTCDATETIME())`).

### Type fidelity (selected columns)

Today everything that isn't `String/Int32/Bool` is `NVARCHAR(MAX)`. V2 uses real types where the source is stable:

| Column | V1 | V2 |
|---|---|---|
| `*.ComputerName` | `NVARCHAR(MAX)` | `NVARCHAR(128)` |
| `SystemInfo.lastbootuptime` | `NVARCHAR(MAX)` | `DATETIME2(3)` |
| `DiskSpace.TotalSize_GB` / `FreeSpace_GB` | `NVARCHAR(MAX)` | `DECIMAL(10,2)` |
| `UserProfileList.UserProfileSizeMB` | `NVARCHAR(MAX)` | `DECIMAL(12,2)` |
| `PersonalCertificates.NotBefore` / `NotAfter` | `NVARCHAR(MAX)` | `DATETIME2(0)` |
| `LocalUsers.PasswordLastSet` / `LastLogonDate` | `NVARCHAR(MAX)` | `DATETIME2(0)` |
| `MPComputerStatus.*SignatureAge` | `NVARCHAR(MAX)` | `INT` |
| `MPComputerStatus.*SignatureLastUpdated` | `NVARCHAR(MAX)` | `DATETIME2(0)` |
| `InstalledUpdates.InstalledOn` | `NVARCHAR(MAX)` (was `Date`) | `DATE` |

The schema-generation code (`CreateSQLTableFromJSON.ps1`) gets a richer type switch covering `DateTime`, `Decimal`, `Int64`, `DateTimeOffset`. Nested arrays / complex objects still serialize to `NVARCHAR(MAX)` JSON — addressed by a future change to child tables.

### Current-state views

The view layer is what Power BI / Grafana / Excel reads. Each metric gets a `vCurrent*` view that selects the latest run's rows per computer.

```sql
CREATE OR ALTER VIEW dbo.vCurrentInstalledSoftware AS
WITH LatestRuns AS (
    SELECT r.ComputerName, r.RunId
    FROM dbo.CollectionRuns r
    INNER JOIN (
        SELECT ComputerName, MAX(StartedAt) AS LatestAt
        FROM dbo.CollectionRuns
        WHERE Status = 'Loaded'
        GROUP BY ComputerName
    ) m ON r.ComputerName = m.ComputerName AND r.StartedAt = m.LatestAt
)
SELECT s.*
FROM dbo.InstalledSoftware s
INNER JOIN LatestRuns lr ON s.RunId = lr.RunId;
```

`InstalledUpdates` is simpler — already row-per-current-install:

```sql
CREATE OR ALTER VIEW dbo.vCurrentInstalledUpdates AS
SELECT * FROM dbo.InstalledUpdates WHERE UninstalledAt IS NULL;
```

Cross-table views for common dashboard questions:

```sql
-- Servers that haven't reported in N days
CREATE OR ALTER VIEW dbo.vStaleComputers AS
SELECT c.*, DATEDIFF(HOUR, c.LastSeenAt, SYSUTCDATETIME()) AS HoursSinceLastSeen
FROM dbo.Computers c
WHERE c.IsActive = 1
  AND c.LastSeenAt < DATEADD(HOUR, -25, SYSUTCDATETIME());   -- 25h grace at daily cadence

-- Fleet software inventory: one row per (software, version) with server count
CREATE OR ALTER VIEW dbo.vFleetSoftware AS
SELECT DisplayName, DisplayVersion, Publisher,
       COUNT(DISTINCT ComputerName) AS InstalledOn
FROM dbo.vCurrentInstalledSoftware
GROUP BY DisplayName, DisplayVersion, Publisher;

-- Certificates expiring in the next 30 days
CREATE OR ALTER VIEW dbo.vExpiringCertificates AS
SELECT ComputerName, Subject, NotAfter,
       DATEDIFF(DAY, SYSUTCDATETIME(), NotAfter) AS DaysToExpiry
FROM dbo.vCurrentPersonalCertificates
WHERE NotAfter < DATEADD(DAY, 30, SYSUTCDATETIME());
```

Power BI / Grafana / Excel point at the `vCurrent*` views by default. Trend dashboards point at the underlying fact tables directly and filter by `RunId IN (...)` or join on `CollectionRuns`.

## Pipeline changes

### `GetInventory.ps1`

- Generate `$RunId = [guid]::NewGuid()` at script start.
- Stamp every metric JSON record with the `RunId` (top-level property).
- Add a `_collection-meta.json` file in the outer zip:

  ```json
  { "RunId": "...", "ComputerName": "...", "StartedAt": "...",
    "MetricsSucceeded": 13, "MetricsFailed": 0, "FailedMetrics": "" }
  ```

  This is what populates `CollectionRuns`.

### `ParseInventory.ps1`

- Read `_collection-meta.json` from each outer zip and emit a `CollectionRuns.json` aggregated file alongside the existing metric JSONs.
- No other change — the `RunId` is already on every row.

### SQL load (`CreateSQLTableFromJSON.ps1` + `UpdateSQLTableFromJSON_new.ps1`)

The biggest change. The current upsert model is replaced by:

1. **Upsert `Computers`** from the distinct `ComputerName` values seen across all JSONs. Update `LastSeenAt` and `LastRunId` for known servers; insert new ones with `FirstSeenAt = SYSUTCDATETIME()`.
2. **Insert `CollectionRuns`** from `CollectionRuns.json`. `Status = 'Loaded'`, `LoadedAt = SYSUTCDATETIME()`.
3. **Insert fact rows append-only** for the snapshot tables. No more `SELECT COUNT` → `UPDATE or INSERT`. Just `INSERT` with the natural-key UNIQUE index providing safety (re-running the same `RunId` is a no-op via `INSERT ... WHERE NOT EXISTS`).
4. **MERGE for `InstalledUpdates`** per the differential model above.

Because the snapshot fact tables are append-only, the script becomes *simpler*: the `KeyColumnsMap` goes away (now expressed as DB constraints). Only `InstalledUpdates` carries the merge-by-natural-key logic.

### Retention

A scheduled job (new script `Run-RetentionPolicy.ps1`, called from `scheduler.ps1` weekly):

```sql
-- Drop snapshot fact rows older than N runs per computer.
-- ON DELETE CASCADE on every fact table's FK does the cleanup.
WITH RankedRuns AS (
    SELECT RunId,
           ROW_NUMBER() OVER (PARTITION BY ComputerName ORDER BY StartedAt DESC) AS rn
    FROM dbo.CollectionRuns
)
DELETE FROM dbo.CollectionRuns
WHERE RunId IN (SELECT RunId FROM RankedRuns WHERE rn > @RetainRuns);

-- Separately: purge old uninstalled InstalledUpdates rows
DELETE FROM dbo.InstalledUpdates
WHERE UninstalledAt IS NOT NULL
  AND UninstalledAt < DATEADD(DAY, -@RetainUninstalledDays, SYSUTCDATETIME());

-- Mark long-silent computers inactive
UPDATE dbo.Computers
SET    IsActive = 0, DeactivatedAt = SYSUTCDATETIME()
WHERE  IsActive = 1
  AND  LastSeenAt < DATEADD(DAY, -@InactiveAfterDays, SYSUTCDATETIME());
```

Defaults:

- `@RetainRuns = 90` (3 months of daily collection)
- `@RetainUninstalledDays = 180`
- `@InactiveAfterDays = 30`

## Storage sizing (rough order of magnitude)

For 1000 servers, daily cadence, 90 days retention:

| Table | Snapshot rows / server | Total rows | Approx storage |
| --- | --- | --- | --- |
| `CollectionRuns` | 90 | 90k | < 50 MB |
| `SystemInfo` | 90 (mostly identical) | 90k | < 100 MB |
| `InstalledSoftware` | 90 × ~100 | 9 M | ~2–4 GB |
| `Services` | 90 × ~50 | 4.5 M | ~1 GB |
| `ScheduledTasks` | 90 × ~30 | 2.7 M | ~500 MB |
| `InstalledUpdates` (differential) | ~500 unique lifetime | 500k | ~150 MB |
| `GroupMembers` | 90 × ~10 | 900k | ~200 MB |

Rough total: **~5–10 GB** across the snapshot tables. Manageable on commodity SQL Server. If a particular table grows louder than expected, the response is per-table retention tightening or columnstore — both can be added without schema change.

## Migration plan

In-place ALTER, three phases. No big-bang drop.

### Phase 1 — infrastructure (zero behavior change)

1. Create `Computers` and `CollectionRuns`.
2. Backfill `Computers` from `DISTINCT ComputerName` across existing fact tables. Set `FirstSeenAt = MIN(UpdateTimeStamp)`, `LastSeenAt = MAX(UpdateTimeStamp)`.
3. `ALTER TABLE` each fact table to add `RunId` (nullable for now) and `CreatedAt` (defaulted to existing `UpdateTimeStamp`).
4. Backfill `RunId` with a single "v1-migration" GUID per computer. Insert matching rows into `CollectionRuns` with `Status = 'Loaded'` and `StartedAt = MAX(UpdateTimeStamp)`.
5. Restructure `InstalledUpdates` into the differential model (drop existing rows, recreate empty — old snapshot data isn't compatible with the differential shape). Fleet will repopulate naturally on the next collection cycle.
6. Tighten `RunId` to `NOT NULL`. Add FKs. Add UNIQUE indexes.
7. Widen `ComputerName` everywhere to `NVARCHAR(128)`.

After Phase 1 the DB has the new shape, existing scripts still work, frontend doesn't exist yet.

### Phase 2 — pipeline emits `RunId`

1. Update `GetInventory.ps1` to generate `RunId` and emit `_collection-meta.json`.
2. Update `ParseInventory.ps1` to aggregate `CollectionRuns.json`.
3. Update load scripts to insert `Computers` / `CollectionRuns` rows.
4. Keep upsert behavior on snapshot tables for one or two collection cycles to validate that `RunId` is being threaded through.

### Phase 3 — switch to append-only + add views + retention

1. Drop the `KeyColumnsMap`-based UPDATE branch in the load script. Snapshot tables become append-only.
2. Switch `InstalledUpdates` load to the differential MERGE pattern.
3. Add the `vCurrent*` views.
4. Add `Run-RetentionPolicy.ps1` and wire it into `scheduler.ps1` (weekly).
5. Drop `UpdateTimeStamp` from each fact table.

After Phase 3, every collection cycle is a new snapshot. Frontend can be built against the views.

## What this doesn't change

- Endpoint code structure: `GetInventory.ps1`'s `Get-*` functions stay as-is, just gain `RunId` on output.
- Zip transport, file share layout, scheduler chain.
- The on-prem vs Azure split — both still need this refactor; Azure variant remains TODO under MSI rewrite.
- Existing tests pass against today's schema. New tests will be added as Phase 1/2/3 land.
